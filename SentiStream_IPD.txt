1. Development Strategy
1.1 Overall Implementation Approach
SentiStream is built as a modular monolith using a bottom-up pipeline strategy: each layer is built, tested, and verified in isolation before the next layer depends on it. This approach eliminates integration surprises, keeps the system demo-stable at every checkpoint, and produces a clean git history with meaningful tagged milestones.
Core philosophy: Every Friday should produce a system that runs end-to-end. Never leave Week N+1 unable to demo what Week N built.
1.2 Build Order Rationale
The pipeline has one direction of data flow: Ingestor → Redis → Worker → [Model + Drift] → ClickHouse → FastAPI → React. Building in this order means:
ML training runs first because the ONNX model artifact is a hard dependency for the worker. Training takes compute time — start it early and let it run in the background.
Infrastructure (Docker, Redis, ClickHouse) comes second because every subsequent component needs a running data store to verify against.
The backend pipeline (ingestor → worker → database) is built before the API because the API only reads what the pipeline produces.
The React dashboard is built last because it is a consumer of a completed backend — building it earlier would require mocking everything.

3. Engineering Task Breakdown
Epic 1: ML Pipeline (16–22 hrs)
Data Prep (2 hrs): Acquire & process Financial PhraseBank. Download Malo et al. dataset; inspect class distribution (2879 pos / 1363 neu / 604 neg); split 80/10/10 stratified by class.
Data Prep (2 hrs): Build DataLoader with class balancing. Use WeightedRandomSampler for class imbalance; apply CrossEntropyLoss weights [1.0, 2.1, 4.8]; verify batch label distribution.
Fine-Tuning (4 hrs): train.py: fine-tune ProsusAI/finbert. HuggingFace Trainer configuration (5 epochs, lr=2e-5, AdamW + warmup); checkpoint saving; handle CUDA/MPS/CPU auto-detect.
Evaluation (2 hrs): evaluate.py: per-class F1 + confusion matrix. Load best checkpoint; compute weighted F1, per-class F1, and confusion matrix PNG; write to benchmark.json.
ONNX Export (4 hrs): export_onnx.py: FP32 → INT8 quantization. Use optimum.exporters.onnx for FP32 export; run ORTQuantizer for INT8 dynamic quantization; benchmark FP32 vs INT8 latency (1000 runs); validate F1 delta < 2%.
Validation (1 hr): Startup integrity check. Compute SHA-256 checksum of finbert-int8.onnx at model load; run sys.exit(1) on mismatch; document checksum in models/README.md.
CI Benchmark (3 hrs): benchmark_ci.py for GitHub Actions. Run 1000 inferences on fixed held-out set; assert p99 < 50ms; fail CI if it regresses > 5ms from committed baseline.
Epic 2: Infrastructure & DevOps (12–16 hrs)
Docker (4 hrs): Multi-service configuration. Configure Redis 7.2-alpine (maxmemory 200mb, LRU policy); ClickHouse 24.3-alpine (init SQL mount, volume); Backend Dockerfile (Python 3.11-slim, non-root USER 1001); Frontend Dockerfile (node:20-alpine); map HuggingFace tokenizer cache volume.
ClickHouse Schema (3 hrs): schema.sql: DDL for all 4 tables + indexes + TTL. Create tables: headlines, inference_telemetry, drift_alerts, paper_trades; build materialized view mv_latency_percentiles (AggregatingMergeTree); enforce 7-day TTL on all tables; build bloom_filter + minmax indexes.
Config (2 hrs): config.py: environment variables. Map variables: FINNHUB_API_KEY, REDIS_URL, CH_HOST/USER/PASSWORD/DB, DRIFT_ALERT_Z_THRESHOLD=2.0, DRIFT_WINDOW_SIZE=100, DRIFT_MIN_SAMPLES=30, POLL_INTERVAL=60, TRADING_STRATEGY, LOG_LEVEL; enforce Pydantic BaseSettings validation on startup.
Secrets (1 hr): Access controls. Draft .env.example with all keys as empty strings with descriptive comments; add .env entry to .gitignore; document detect-secrets pre-commit hook setup instructions in CONTRIBUTING.md.
CI/CD (4 hrs): GitHub Actions implementation. Define 5 jobs (lint, test, ml-benchmark, security, frontend); execute ruff lint + format checks; assert pytest coverage $\ge 80\%$ with a Redis service container; integrate pip-audit and npm audit --audit-level=critical.
Seed Script (2 hrs): seed_test_data.py: synthetic injection. Add --mode=drift: insert 50 high-confidence-positive records to trigger Z-score alert for AAPL; add --mode=bulk: insert pre-captured Finnhub headlines for offline demo workflows.
Epic 3: Data Ingestion (10–14 hrs)
Finnhub Client (3 hrs): Async polling implementation. Poll GET /news?category=general every POLL_INTERVAL seconds; parse response JSON into HeadlineRaw Pydantic model; handle HTTPError, JSONDecodeError, and asyncio.TimeoutError.
Rate Limiter (2 hrs): Traffic throttling. Enforce token bucket limiter with 60 req/min ceiling; add configurable FINNHUB_MAX_REQ_PER_MIN; log warnings at 80% utilization to prevent exceeding limits.
Deduplication (2 hrs): Identity management. Generate sha256(headline_text + ticker) hex digest; run SETNX sentistream:seen:{hash}; apply a 24-hour TTL ($86400\text{s}$) on new keys; log metrics.
RSS Fallback (3 hrs): Source failover. Parse 3-5 financial RSS feeds (Reuters, MarketWatch, Yahoo Finance) via feedparser; activate automatically on Finnhub 429/5xx errors; normalize text to unified schema; deactivate when Finnhub recovers.
Redis Producer (2 hrs): Message streaming. Serialize payload to JSON; execute XADD raw_headlines MAXLEN ~ 1000 * {id, ticker, headline_text, source, ingested_at}; emit Prometheus gauge ingestor_headlines_ingested_total{source}.
Error Handling (2 hrs): Resilience structures. Integrate structlog JSON logging for all pipeline lifecycle events; map ingestor_errors_total counter; implement exponential backoff on connection loss (1s, 2s, 4s, up to 30s max).

6. Database Implementation Order
6.1 Table Creation Sequence
All database storage schemas are contained within schema.sql and initialized idempotently during application startup using IF NOT EXISTS declarations.

headlines: The primary entity table. All subsequent data records map back to a corresponding headline_id or join across its ticker classifications. Must be initialized first.
inference_telemetry: Logs performance metadata linked to headline_id. Constructed immediately after core entities to maintain database architecture relationships.
drift_alerts: Tracks system context states; maps target records explicitly against ticker indexes. Initialized third to group metrics tables together.
paper_trades: Logs transaction histories linked to signal IDs. Part of Phase 2 capabilities, though structural placeholders exist in initial schemas.
mv_latency_percentiles (Materialized View): Computes analytics aggregates straight from the telemetry logs. Requires the source tables to be defined first.
6.2 Migration Plan
SentiStream v1 uses an idempotent schema execution framework at application startup, removing the need for a heavy migration engine during the initial MVP. As development scales through subsequent phases, operations migrate to structured execution tracks:
migrations/001_initial_schema.sql — Captures baseline database and view configurations.
migrations/002_add_trading_strategy_column.sql — Modifies active schemas to append operational context parameters (Phase 2).
migrations/003_add_non_english_headlines_table.sql — Establishes separate tables for filtering non-English records (Phase 2).
Execution Engine: A lightweight file iteration runner tracks updates inside a schema version ledger table at startup.
