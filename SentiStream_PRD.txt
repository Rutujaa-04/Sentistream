1. Executive Summary
1.1 Product Overview
SentiStream is a production-grade, open-source MLOps pipeline that ingests live financial news headlines, applies FinBERT-based NLP sentiment classification, detects statistical model drift, and powers a quantitative paper trading engine — all exposed through a real-time observability dashboard. Built with FastAPI, Redis Streams, ClickHouse, ONNX Runtime, and React, SentiStream represents the full surface area of a modern AI-infused data platform.

Interview Soundbite: "SentiStream is not just a sentiment classifier — it is a full-stack MLOps system demonstrating my ability to design, build, and operate AI pipelines at production scale, from data ingestion through model inference, drift detection, and real-time visualization."

"To be the most technically complete, interview-ready, open-source reference implementation of a real-time financial NLP and MLOps pipeline — demonstrating the full stack from raw data ingestion to quantitative signal generation."

Quantitative sentiment analysis applied to financial markets is a mature institutional practice. Hedge funds and proprietary trading desks (Two Sigma, Citadel, Renaissance Technologies) have built internal NLP pipelines for over a decade. Retail and open-source equivalents, however, are fragmented: either academically-focused with no production plumbing, or SaaS-gated behind expensive APIs. The convergence of several trends makes a portfolio-grade implementation both possible and timely:
Pre-trained financial language models (FinBERT, BloombergGPT) are now publicly available.
Cloud-native streaming infrastructure (Redis Streams, Apache Kafka) has democratized event-driven architectures.
ONNX Runtime enables CPU-viable, sub-10ms inference without GPU infrastructure.
ClickHouse delivers OLAP query performance suitable for millisecond telemetry analytics on a laptop.

8. Functional Requirements
FR-001: News Ingestion Pipeline
Description
Continuous ingestion of live financial news headlines with primary (Finnhub) and fallback (RSS) sources.
User Flow
1. Scheduler triggers ingestor.py every 60s → 2. Calls Finnhub /news API → 3. Deduplicates by headline hash → 4. Publishes to Redis Stream → 5. On Finnhub failure, falls back to RSS feeds.
Inputs
Finnhub API key (env var), RSS feed URLs (config), polling interval (config).
Outputs
Deduplicated headline messages in Redis Stream with ticker symbol, headline text, source, and timestamp.
Edge Cases
Finnhub rate limit hit (60 req/min), RSS feed timeout, duplicate headline from multiple sources, malformed JSON response.
Validation Rules
Headline must have non-null text and timestamp. Ticker symbol must be non-empty string.
Acceptance Criteria
Headlines appear in Redis Stream within 5s of Finnhub response. DLQ captures malformed messages. RSS fallback activates within 10s of Finnhub failure.

FR-002: ONNX Inference Engine
Description
Sub-50ms (p99) INT8-quantized FinBERT inference on CPU via ONNX Runtime.
User Flow
1. Worker consumes headline from Redis Stream → 2. Tokenizes text (max 512 tokens) → 3. Runs ONNX InferenceSession → 4. Returns {label, confidence, latency_ms}.
Inputs
Raw headline string (str, max 512 chars).
Outputs
JSON: {label: "positive"|"negative"|"neutral", confidence: float [0,1], latency_ms: float}.
Edge Cases
Text > 512 tokens (truncate with warning), non-English text (flag as undefined), ONNX session load failure on startup.
Validation Rules
Confidence must sum to 1.0 across all three classes. Latency must be recorded regardless of outcome.
Acceptance Criteria
p99 inference latency < 50ms measured over 1,000 consecutive inferences. F1 ≥ 0.88 on held-out Financial PhraseBank test set.

FR-003: Z-Score Drift Detection
Description
Statistical drift detection on rolling sentiment distribution using configurable Z-score threshold.
User Flow
1. After each inference, drift.py updates rolling mean and std → 2. Computes Z-score of current sentiment → 3. If |Z| > DRIFT_ALERT_Z_THRESHOLD, publishes alert to ClickHouse drift_alerts table → 4. Dashboard displays alert in Analytics.jsx.
Inputs
Sentiment score sequence (floats), window size (config, default 100), threshold (config, default 2.0).
Outputs
DriftAlert record: {ticker, z_score, timestamp, direction, triggered_threshold}.
Edge Cases
Insufficient history (< window_size samples): suppress alerts. All-neutral sentiment baseline: alerts may be hyper-sensitive (document this behavior).
Validation Rules
Z-score must be a finite float. Window must have minimum 30 samples before alerting.
Acceptance Criteria
seed_test_data.py synthetic drift injection triggers alert within 5 seconds. No false positives on stable baseline over 1,000-sample run.

FR-004: Real-Time WebSocket Dashboard
Description
React dashboard with three components: LiveTicker, Observability (latency percentiles), and Analytics (trends + drift).
User Flow
1. User opens browser → 2. React app connects to FastAPI WebSocket → 3. New sentiment events streamed in real time → 4. LiveTicker scrolls headlines → 5. Charts update without page refresh.
Inputs
WebSocket stream from FastAPI /ws endpoint.
Outputs
Live sentiment labels, scrolling ticker, p50/p95/p99 latency charts, Z-score timeline, drift alert badges.
Edge Cases
WebSocket disconnect (auto-reconnect with exponential backoff). No data for > 60s (show "Waiting for data..." state). Browser tab hidden (pause render, not data).
Acceptance Criteria
Dashboard loads in < 2s. New sentiments appear within 1s of inference completion. Latency charts reflect real p-values from ClickHouse.

FR-005: Paper Trading Engine
Description
Quantitative signal engine that converts sentiment scores into simulated buy/sell/hold decisions with position sizing and P&L tracking.
Signal Logic Options
Option A (Simulated Only): Internal position tracking, no broker API. Option B (Read-Only): Alpaca paper account view. Option C (Full Execution): Alpaca API order submission.
User Flow
1. Sentiment score ingested → 2. Signal generator applies confidence threshold → 3. Position sizing applies Kelly Criterion or fixed-fraction → 4. Order logged to ClickHouse → 5. P&L updated in dashboard.
Inputs
Sentiment {label, confidence}, current position (from ClickHouse), available capital (config).
Outputs
Trade order: {ticker, action, quantity, price_at_signal, timestamp, rationale}.
Edge Cases
Duplicate signals within 60s (cooldown period), confidence below threshold (no trade), portfolio at max exposure.
Acceptance Criteria
Signal generation latency < 100ms. P&L calculation matches manual verification. All trades logged with full audit trail.

FR-006: Health Check & Connection Warmup
Description
A /ping endpoint that actively warms ClickHouse and Redis connections to prevent cold-start failures during demos.
User Flow
Startup script calls GET /ping → FastAPI executes SELECT 1 on ClickHouse + redis.ping() → Returns {status: "ok", clickhouse: "warm", redis: "warm"}.
Acceptance Criteria
/ping responds within 2s. Subsequent pipeline operations show no cold-start latency spike.

11. User Flows
11.1 Local Setup & Onboarding Flow
Step 1: Clone repository — git clone github.com/rutuja/sentistream
Step 2: Copy .env.example → .env, add Finnhub API key.
Step 3: Run docker-compose up — spins up Redis, ClickHouse, FastAPI backend.
Step 4: Run npm install && npm run dev in /frontend — Vite dev server starts on localhost:5173.
Step 5: Startup script auto-calls GET /ping to warm connections.
Step 6: Dashboard loads. LiveTicker shows first headlines within 60 seconds.
Step 7 (Optional Demo): Run python scripts/seed_test_data.py to inject synthetic drift and trigger alert.
11.2 Core Pipeline Flow (Per Headline)
T+0s: Ingestor polls Finnhub API for /news?category=general.
T+0.1s: Headline deduplication check (SHA-256 hash against Redis SET).
T+0.2s: Headline published to Redis Stream as JSON message.
T+0.3s: Worker consumer group reads message from stream.
T+0.5s: ONNX InferenceSession runs FinBERT on headline text.
T+0.55s: Sentiment result {label, confidence, latency_ms} returned.
T+0.6s: Result written to ClickHouse (headlines table + telemetry table).
T+0.65s: Drift detection runs; alert written if threshold exceeded.
T+0.7s: FastAPI WebSocket broadcasts event to all connected React clients.
T+0.8s: Dashboard updates LiveTicker, Observability charts, Analytics panel.
11.3 Error Handling Flow
Finnhub API failure → ingestor.py catches exception → logs warning → activates RSS fallback → continues polling.
ONNX inference failure → worker.py catches exception → routes message to DLQ stream → logs error with full message context → continues processing next message.
ClickHouse connection failure → database.py raises exception → worker.py catches → retries 3x with exponential backoff → routes to DLQ if all retries fail.
WebSocket client disconnect → FastAPI removes client from broadcast list → client-side auto-reconnects with exponential backoff.
Redis connection failure → All services fail with clear error log → /health endpoint returns 503 → startup script alerts operator.
11.4 Live Demo Flow (Interview Context)
Interviewer present: Open browser to localhost:5173 — dashboard immediately visible.
Explain LiveTicker: "This is pulling real headlines from Finnhub and classifying each one with a fine-tuned FinBERT model served via ONNX Runtime."
Explain Observability panel: "These p50/p95/p99 latency values are real — queried live from ClickHouse, not mocked."
Trigger drift: python scripts/seed_test_data.py --mode=drift → alert fires in Analytics panel within 5 seconds.
Explain alert: "This Z-score alert fired because the rolling sentiment distribution shifted beyond 2 standard deviations — that's the 95th percentile of a normal distribution."

13. Technical Architecture
13.1 Architecture Overview
Architecture Decision Record: SentiStream is designed as a decoupled, event-driven pipeline where each component (ingestor, worker, inference, drift, API, database) is independently replaceable. This is intentional — it makes the architecture story richer and more interview-defensible than a monolithic approach.

Layer
Technology
Architectural Rationale
Frontend
React 18 + Vite + Recharts + WebSocket API
Vite hot reload accelerates development; WebSocket provides true push semantics without polling.
API Layer
FastAPI (Python 3.11) + uvicorn
Native async/await for concurrent WebSocket + REST handling; automatic OpenAPI docs for interviewer review.
Message Broker
Redis Streams (Upstash-compatible)
Consumer groups provide at-least-once delivery and parallelism without Kafka's operational overhead.
ML Inference

13.2 Key Architectural Decisions & Trade-offs
Redis Streams vs. Apache Kafka
Redis Streams was chosen over Kafka for this portfolio context. Kafka would be architecturally superior for true production scale (partitions, replication, retention policies) but adds significant operational complexity (Zookeeper/KRaft, broker configuration) with no portfolio benefit for a single-node demo. The consumer group semantics are functionally identical for demonstrating the core concept. This trade-off is documented in ARCHITECTURE.md and is a rich interview discussion point.

ONNX Runtime vs. TorchServe vs. Triton Inference Server
ONNX Runtime was selected for CPU-only inference. TorchServe and Triton Inference Server are production-grade choices but require GPU infrastructure to realize their value. ONNX Runtime's Python API is sufficient for demonstrating the inference serving concept on a laptop, and INT8 quantization provides a concrete optimization story with measurable latency benchmarks.

ClickHouse vs. PostgreSQL + TimescaleDB
ClickHouse delivers sub-millisecond aggregation on time-series telemetry data at scale. PostgreSQL with TimescaleDB would be more conventional but would require query optimization that ClickHouse handles natively. The interview story for choosing ClickHouse ("I needed OLAP-native latency percentile queries without query tuning") is cleaner and signals broader database knowledge.
13.3 Component Dependency Graph
Ingestor → Redis Stream → Worker → [ONNX Model | Drift Detector] → ClickHouse → FastAPI WebSocket → React Dashboard. All dependencies flow left-to-right. No circular dependencies. Each component can be tested in isolation.

Appendix: Interview Story Templates
The following are prepared talking-point structures for common interview questions. These can be adapted and practiced verbatim.

"Tell me about a complex system you designed."
SentiStream is a real-time financial NLP pipeline I architected and built. It ingests live news headlines via Finnhub, classifies each one using a fine-tuned FinBERT model I serve with ONNX Runtime at under 50ms p99 latency, detects statistical drift via Z-score analysis, and streams results to a React dashboard backed by ClickHouse for sub-millisecond latency percentile queries. The key architectural decision I made was to use Redis Streams with consumer groups instead of Kafka — a deliberate trade-off that gives me the same at-least-once delivery semantics with dramatically lower operational overhead for this scale.

"How would you handle model drift in production?"
In SentiStream I implemented a Z-score based drift detector in drift.py. It maintains a rolling window of sentiment scores, computes the mean and standard deviation, and fires an alert when the current distribution shifts beyond 2.0 standard deviations — which corresponds to the 95th percentile of a normal distribution. The threshold is externalized to config.py as DRIFT_ALERT_Z_THRESHOLD so it can be tuned without a code deploy. I also built a seed_test_data.py script that synthetically injects drift so I can verify the alert pipeline without waiting for natural distribution shifts.

"Why ONNX Runtime over TorchServe?"
For this use case, ONNX Runtime was the right choice for three reasons: First, I am running on CPU only — ONNX Runtime is highly optimized for CPU inference and supports INT8 quantization, which gave me a 3-4x latency improvement over the base PyTorch model. Second, ONNX decouples the runtime from the training framework — if I switch from PyTorch to a JAX-based model in the future, the serving layer does not change. Third, TorchServe and Triton Inference Server are excellent tools, but they add operational complexity that is not justified without a GPU and multi-model serving requirements. I documented this decision in ARCHITECTURE.md precisely because I expected it to be a system design discussion point.
