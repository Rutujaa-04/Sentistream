1. Technical Overview
1.1 System Purpose
SentiStream is a production-grade, event-driven MLOps pipeline that ingests live financial news headlines, runs quantized FinBERT NLP inference, detects statistical model drift, and delivers real-time observability via a WebSocket-powered React dashboard — all on 100% free-tier infrastructure.

3. Architecture Decisions (ADRs)
ADR-001: Redis Streams vs. Apache Kafka
Decision: Redis Streams with consumer groups (Upstash free tier)
Alternatives Considered: Apache Kafka (Confluent Cloud free tier) | RabbitMQ | In-process asyncio queue
Trade-offs: Redis: 256MB memory cap on free tier; no compaction; no infinite retention. Kafka: full partition replication semantics, better at scale, but Zookeeper/KRaft adds 2+ services; Confluent free tier has cluster restrictions. RabbitMQ: no native consumer group replay.
Final Reasoning: Consumer group semantics (at-least-once, parallel workers, XPENDING for lag monitoring) are functionally identical to Kafka for this throughput. Upstash Redis is serverless with a generous free tier and zero ops overhead. Kafka would add 300+ lines of config for no functional gain at this scale. Upgrade path to Kafka documented in ARCHITECTURE.md.
ADR-002: ONNX Runtime vs. TorchServe vs. Triton Inference Server
Decision: ONNX Runtime 1.17 with INT8 dynamic quantization
Alternatives Considered: TorchServe | Triton Inference Server | vLLM | Direct PyTorch (torch.inference_mode)
Trade-offs: ONNX Runtime: CPU-optimized, no GPU needed, portable, INT8 quantization supported. TorchServe: requires JVM, complex model-store configuration, GPU-optimized. Triton: GPU-first, multi-model serving overkill for single model. Direct PyTorch: 3-4x slower than quantized ONNX on CPU.
Final Reasoning: FinBERT served via ONNX Runtime achieves p99 < 50ms on CPU (vs ~180ms unquantized PyTorch). INT8 dynamic quantization provides ~3.5x speedup with < 1% F1 degradation on Financial PhraseBank. Framework-agnostic: switching from PyTorch to JAX or a different base model requires only re-exporting ONNX — the serving layer is unchanged. Triton is the correct choice at scale with GPU; documented as Phase 3 upgrade.
ADR-003: ClickHouse vs. PostgreSQL + TimescaleDB vs. InfluxDB
Decision: ClickHouse (ClickHouse Cloud free tier, Docker for local)
Alternatives Considered: PostgreSQL + TimescaleDB extension | InfluxDB Cloud free tier | DuckDB (embedded)
Trade-offs: ClickHouse: columnar OLAP, sub-ms aggregation, native p-quantile functions. PostgreSQL/TimescaleDB: row-oriented, needs query tuning for percentile aggregations at volume, TimescaleDB extension adds ops complexity. InfluxDB: time-series native but limited SQL, small free tier. DuckDB: zero-ops embedded OLAP but no concurrent writers.
Final Reasoning: quantile(0.99)(latency_ms) executing over 100k rows returns in < 5ms natively in ClickHouse with no indexing. This is the interview story: "I chose ClickHouse because p99 latency computation is a native columnar scan — not a sort operation." Dashboard percentile charts query live data, not cached aggregations. Upgrade path: self-hosted ClickHouse on Railway free tier, then dedicated cluster.
ADR-004: FastAPI vs. Django REST Framework vs. Flask vs. Express.js
Decision: FastAPI (Python 3.11, uvicorn, async-first)
Alternatives Considered: Django REST Framework | Flask + flask-socketio | Express.js + socket.io
Trade-offs: FastAPI: async/await native, WebSocket support built-in, automatic OpenAPI docs, Pydantic validation. Django REST: sync-first, heavyweight for a real-time pipeline API, ORM not needed. Flask: manual WebSocket via flask-socketio, no async, no validation. Express.js: requires Node.js runtime separate from Python ML stack.
Final Reasoning: FastAPI's async WebSocket handler allows concurrent client connections without threading overhead. Pydantic models document the API contract for interviewers. Auto-generated OpenAPI at /docs serves as living documentation. Critical for portfolio: FastAPI is the dominant Python API framework in ML/MLOps roles — direct signal to interviewers.
ADR-005: Monolith vs. Service-Per-Component vs. Serverless Functions
Decision: Modular monolith with logical boundaries (single Python process, importable modules)
Alternatives Considered: Microservices (separate Docker containers per component) | Serverless (AWS Lambda free tier) | Celery workers
Trade-offs: Microservices: true isolation, independent scaling, but 5+ Docker containers for a single-dev portfolio project is operationally excessive and complicates docker-compose demo reliability. Serverless: cold start latency incompatible with < 500ms SLA; AWS Lambda free tier has 1M invocation limit. Celery: adds Redis+broker coupling, overkill for 100 headlines/min.
Final Reasoning: The modular monolith is the correct trade-off: ingestor.py, worker.py, model.py, drift.py, database.py are logically separated with clean interfaces — they could be extracted to microservices without changing business logic. This architecture demonstrates separation of concerns and hexagonal design to interviewers, while maintaining a single docker-compose up demo experience.
ADR-006: React 18 vs. Next.js vs. Vue 3 vs. Svelte
Decision: React 18 with Vite, Recharts, native WebSocket API
Alternatives Considered: Next.js (SSR overkill for dashboard) | Vue 3 | Svelte | Angular
Trade-offs: Next.js: SSR adds complexity for a real-time SPA — no SEO requirement for a dashboard. Vue 3/Svelte: smaller community signal for ML engineering roles. React: dominant in fintech dashboards (Bloomberg Terminal UI, Robinhood, Coinbase all React-based).
Final Reasoning: React 18 with concurrent features is the highest interview-signal choice for a fintech dashboard. Recharts is React-native for financial visualization. Vite provides sub-second HMR. The native WebSocket API (no socket.io dependency) demonstrates direct protocol knowledge — interviewers can ask "how does your WebSocket reconnect?" and receive a concrete implementation answer.
ADR-007: Upstash Redis vs. Local Redis vs. Railway Redis vs. Render Redis
Decision: Local Redis (Primary) / Upstash Redis (Cloud fallback)
Alternatives Considered: Local Redis in Docker | Railway Redis (500MB free) | Render Redis (90-day trial) | Redis Cloud free tier
Trade-offs: Upstash: HTTP-based serverless Redis, 10k commands/day free, global replication, zero ops. Local Docker: zero latency but not cloud-demonstrable. Railway/Render: more storage but 90-day trial expiry or paid after threshold.
Final Reasoning: For demo purposes: local Docker Redis (zero latency, unlimited operations) is PRIMARY. Upstash is documented as the cloud upgrade path — same Redis Streams API, demonstrating cloud-native Redis knowledge without incurring cost. Both environments use identical connection strings via .env — switching requires only changing REDIS_URL.

5. Detailed Module Breakdown
Module 1: ingestor.py — News Ingestion
Purpose: Primary data ingestion loop. Owns all external API interaction.
Responsibilities: Poll Finnhub /news every 60s; apply token-bucket rate limiter (60 req/min); deduplicate via Redis SET SETNX; fallback to RSS on 429/5xx; publish to raw_headlines Redis Stream; log all source events with structlog.
Dependencies: aiohttp (HTTP), redis.asyncio (stream XADD, SET SETNX), feedparser (RSS), config.py (FINNHUB_API_KEY, POLL_INTERVAL)
Inputs: Finnhub API response: [{headline, ticker, datetime, source}]; RSS feed XML
Outputs: Redis Stream message: {id: SHA256_hash, ticker, headline_text, source, ingested_at_unix}
Error Handling: HTTPError → activate_rss_fallback(); JSONDecodeError → log + skip; Redis connection lost → retry 3x exponential backoff; all errors emit Prometheus counter ingestor_errors_total
Key Design: Deduplication SET key: sentistream:seen:{sha256_hash}, TTL: 24h. This prevents reprocessing without unbounded memory growth.
Module 2: worker.py — Consumer Group Manager
Purpose: Redis Stream consumer group manager. Orchestrates inference pipeline per message.
Responsibilities: XREADGROUP loop; deserialize message; call model.infer(); call drift.update(); write to ClickHouse; XACK on success; XADD to DLQ + XACK on failure; broadcast to FastAPI via internal asyncio Queue.
Dependencies: model.py (inference), drift.py (Z-score), database.py (CH writes), redis.asyncio, config.py
Inputs: Redis Stream message from raw_headlines group sentistream_workers
Outputs: ClickHouse writes; asyncio broadcast queue entry; DLQ entry on error
Consumer Group Config: Group: sentistream_workers, Consumer: worker_{PID}, BLOCK: 1000ms, COUNT: 10 (batch reads)
Retry Policy: No in-worker retry — fail fast to DLQ. Retries are an operational decision, not a code decision. XPENDING exposes stuck messages.
Module 3: model.py — ONNX Inference Engine
Purpose: Stateless, decoupled ML inference. No I/O, no state — pure function over text.
Responsibilities: Load ONNX model at startup (singleton); tokenize input (HF AutoTokenizer); run InferenceSession; return typed InferenceResult dataclass; record latency_ms.
Dependencies: onnxruntime (InferenceSession), transformers (AutoTokenizer), numpy
Inputs: headline_text: str (max 512 chars; truncated if longer)
Outputs: InferenceResult(label: Literal["positive","negative","neutral"], confidence: float, latency_ms: float)
Quantization: INT8 dynamic quantization via optimum.onnxruntime.ORTQuantizer. Profiled against FP32 baseline: ~3.5x speedup, < 0.8% F1 delta on Financial PhraseBank test set.
Fallback: If ONNX session load fails at startup: log CRITICAL + sys.exit(1). No silent degradation — a broken model is a hard failure.
Module 4: drift.py — Statistical Drift Detector
Purpose: Stateful Z-score drift detection on rolling sentiment distribution.
Responsibilities: Maintain deque of sentiment scores (maxlen = DRIFT_WINDOW_SIZE, default 100); compute rolling mean + std; compute Z-score of latest score; return DriftSignal if $|Z| > \text{DRIFT\_ALERT\_Z\_THRESHOLD}$ (default 2.0).
Dependencies: collections.deque, numpy, config.py (DRIFT_WINDOW_SIZE, DRIFT_ALERT_Z_THRESHOLD)
Inputs: confidence_score: float, ticker: str
Outputs: Optional[DriftSignal(z_score, direction, window_mean, window_std, triggered_threshold)]
Guard: Suppress alerts if deque length < 30 (insufficient baseline). Configurable via DRIFT_MIN_SAMPLES.
Thread Safety: drift.py is instantiated per-worker. No shared state. Per-ticker drift tracking requires DriftDetector registry in worker.py.
Module 5: database.py — ClickHouse Abstraction
Purpose: Typed ClickHouse client. All SQL is here — no raw queries in workers or API.
Responsibilities: Connection pooling; typed insert methods per table; query methods for /metrics and /analytics endpoints; schema migration on startup.
Key Methods: insert_headline(HeadlineRecord); insert_telemetry(TelemetryRecord); insert_drift_alert(DriftAlert); query_latency_percentiles(window: str) → PercentileResult; query_sentiment_trends(ticker, hours) → list[SentimentBucket]
ClickHouse Config: ENGINE: MergeTree() ORDER BY (ticker, processed_at); TTL: processed_at + INTERVAL 7 DAY; Compression: LZ4
Materialized Views: mv_latency_percentiles: pre-aggregates quantile(0.5,0.95,0.99)(latency_ms) per 1-minute bucket. Dashboard queries this view — not the raw table.
Module 6: main.py — FastAPI Application
Purpose: API gateway, WebSocket hub, health orchestrator.
Responsibilities: WebSocket connection registry; broadcast loop from internal asyncio Queue; /ping warmup (SELECT 1 on CH + Redis PING); /health (component status); /metrics (Prometheus format); REST endpoints for dashboard historical queries.
WebSocket Pattern: asyncio.Queue as bridge between worker.py and WebSocket broadcast. Workers enqueue; broadcast coroutine dequeues and fans out to all connected clients. Dead connections removed on write failure.
Lifespan: FastAPI lifespan context manager: startup → load ONNX model + warm CH/Redis + create consumer group + start ingestor task + start worker task. Shutdown → graceful flush.
Module 7: Paper Trading Engine (trading.py)
Purpose: Converts sentiment signals into simulated buy/sell/hold decisions with P&L tracking.
Signal Strategy: Strategy interface: BaseStrategy.generate_signal(inference_result) → TradeSignal. Default: ThresholdStrategy (buy if positive + confidence > 0.75, sell if negative + confidence > 0.75, else hold).
Position Sizing: Fixed-fraction: 5% of simulated portfolio per signal. Kelly Criterion documented as Phase 2 upgrade.
P&L Tracking: Simulated portfolio state in ClickHouse paper_trades table. Unrealized P&L calculated against mock price feed (Finnhub free /quote endpoint).
Extensibility: New strategies implement BaseStrategy.generate_signal(). Strategy registry in config.py: TRADING_STRATEGY = "threshold" | "mean_reversion" | "momentum".

8. Authentication & Authorization
8.1 v1 Stance (Portfolio Project)
SentiStream v1 has NO authentication. The system processes public financial news, stores no PII, and is designed for single-user local demo use. This is an explicit, documented architectural decision — not an oversight.
The absence of auth in v1 is interview-defensible: "I made the conscious decision to exclude auth for v1 because it adds complexity without enabling any portfolio value. The system handles no user data and no private financial data. Auth would be Phase 2 if SentiStream were productized."

session.run(None, {"input_ids": ids, "attention_mask": mask, "token_type_ids": types}). Output: logits shape [1, 3]. softmax → [pos_prob, neg_prob, neu_prob].
Label Mapping
{0: "positive", 1: "negative", 2: "neutral"} — matches ProsusAI/finbert label ordering. argmax of softmax = predicted label.
Latency Budget
Tokenization: ~3ms | ONNX session run: ~20ms | Post-processing: ~0.5ms | Total: ~24ms mean, ~47ms p99 (measured on Apple M2, expected ~42ms mean on commodity x86)
Non-English Text
Detected via langdetect. If not English: label="undefined", confidence=0.0. Routed to separate CH table non_english_headlines.
9.3 Drift Detection Algorithm

Python
class DriftDetector:    def __init__(self, window_size=100, z_threshold=2.0, min_samples=30):        self.window = deque(maxlen=window_size)        self.z_threshold = z_threshold        self.min_samples = min_samples    def update(self, score: float, ticker: str) -> Optional[DriftSignal]:        self.window.append(score)        if len(self.window) < self.min_samples:            return None  -- Insufficient baseline        arr = np.array(self.window)        mean, std = arr.mean(), arr.std()        if std < 1e-10:  -- Degenerate case: all same score            return None        z = (score - mean) / std        if abs(z) > self.z_threshold:            return DriftSignal(                ticker=ticker,                z_score=round(z, 4),                direction="bullish_spike" if z > 0 else "bearish_spike",                window_mean=round(mean, 4),                window_std=round(std, 4),                triggered_threshold=self.z_threshold,            )        return None# Interview talking point:# Z-score of 2.0 = 95th percentile under normal distribution.# A Z > 2.0 means the current sentiment score is 2 standard deviations# above the rolling 100-headline mean — statistically unusual, not noise.

>= 0.88. Weighted accounts for class imbalance (positive: 2879, neutral: 1363, negative: 604). Macro F1 would penalize majority class.

Negative class F1 >= 0.80 (hardest class). Negative headlines are most impactful for trading signals — false negatives are costly.
Inference Latency (p99)

>= 95% on seed_test_data.py synthetic drift injection. Measured by comparing DriftAlert timestamps to known injection timestamps.

11.1 Retry Policy
Design decision: No in-worker retry loops. SentiStream follows the "fail fast to DLQ" pattern. A failed message is immediately moved to dlq_headlines and XACKed. This prevents worker starvation, avoids thundering herd on downstream failures, and produces a clean audit trail. DLQ replay is a manual operational action — not automated.

"Adding a second worker.py process requires zero code changes — the consumer group distributes automatically. Dedup keys prevent double-processing."
ML Serving / MLOps
ONNX Runtime INT8; model singleton; latency SLA; benchmark CI
"INT8 dynamic quantization gave me a 3.5× latency improvement with < 1% F1 degradation. I validate this in CI — PRs are blocked if p99 regresses > 5ms."
Statistical Modeling
Z-score drift detection; rolling window; configurable threshold
"The Z-score threshold of 2.0 represents the 95th percentile of a normal distribution. A spike above it means the sentiment shift is statistically significant, not noise."
System Design
Hexagonal architecture; ADRs; single docker-compose; modular monolith
"Every module has a clean interface — model.py is a pure function. I could replace FinBERT with GPT-4 by changing model.py alone, nothing else."
Observability
structlog JSON; Prometheus /metrics; Grafana; ClickHouse MVs
"I pre-aggregate latency percentiles in a ClickHouse materialized view — dashboard queries hit < 2ms vs 50ms raw scan. The Prometheus metrics expose DLQ depth for alerting."
Database Engineering
ClickHouse columnar OLAP; MergeTree; TTL; materialized views
"ClickHouse's native quantile() function over a MergeTree table executes a columnar scan — no B-tree index overhead. It's architecturally correct for time-series aggregation."
API Design
FastAPI async; WebSocket push; Pydantic v2; OpenAPI docs; /ping
"The /ping endpoint isn't just a health check — it's a connection warmer. Calling it before the demo ensures ClickHouse and Redis are not in cold-start state."
DevOps / CI/CD
GitHub Actions; Ruff; pytest-cov; pip-audit; ONNX benchmark gate
"My CI pipeline has a dedicated ml-benchmark job that runs inference against a fixed dataset and blocks the PR if p99 exceeds baseline. Latency regression is caught before merge."
Security Engineering
Secrets management; detect-secrets; pip-audit; ONNX checksum; non-root
"I verify the ONNX model checksum at startup — a tampered model is a hard failure, not a silent degradation. Secrets are blocked at commit via detect-secrets pre-commit hook."
Quantitative Finance
Sentiment signal generation; confidence threshold; position sizing; P&L tracking
"The trading signal only fires if confidence exceeds 0.75 — below that, it's a hold. This prevents the model from trading on uncertain predictions."
